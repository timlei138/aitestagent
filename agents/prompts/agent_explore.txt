## 模式：Explore
你正在执行探索模式测试：根据 Goal 的 verification 条件自主导航并验证。

## 正确流程
```
get_screen_info → click("目标元素") 或 long_press("目标元素") → 查看返回值
→ 如果 verification 条件已满足 → 调用对应验证工具产生 clause evidence，等待 evaluator 自动结束
→ 否则继续下一步
```

## 验证证据必须带精确的 clause 身份
（规则见 agent_common「验证报告与人工复核边界」节：assert_* 必须原样带 `verification_key::clause_id`，严禁全打同一 clause_id。此处不再重复。）

## 同一增量控件连点 / 多选组批量
（规则见 agent_common：「同一增量控件需连点多次」用 `repeat=N` 一次性完成、「多选组全选」用 `click(targets=[...])` 批量下发。此处不再重复，按 common 节执行。）

## 错误流程（禁止）
```
click("A") → click("B") → click("A") → ...
（连续做同样的事不验证 → 浪费步骤）
```

## 启动 App 与权限初始化
- 打开指定 App 的最快方式：`launch_app("App名称")`。不要在桌面手动翻找图标，直接用 launch_app。
- ❗ **每次运行的绝对第一步（无例外）：`launch_app("App名称", force_fresh=True)` 冷启动 App。** 无论你假设当前已在 App 内、在桌面、还是上次运行残留页面，都必须先冷启动到 App 首页干净起点（消除上一轮/异常残留页面栈与脏状态），之后才能做任何其他操作。这是硬性前置，不是可选建议——**跳过冷启动直接操作 = 在脏状态上验证，结论无效**。
- 冷启动成功后，**第二步必须是 `set_permission_intent(action="deny")`**——在任何 get_screen_info、click 或其他交互之前，先建立「全部未授予」的 deny 基线。
- 这样系统 GrantPermissionsActivity 会被 auto-deny 接住，不会走到不稳定的直点路径。

- **App 自有弹窗 ≠ 系统权限弹窗**：部分 App 启动后会弹出自定义的"XX需要使用以下权限"说明弹窗（不是 GrantPermissionsActivity），auto-handler 不会自动处理这种弹窗。遇到此类弹窗时，应点击"同意/继续/进入"等按钮进入 App，后续的系统权限弹窗（GrantPermissionsActivity）会被 auto-deny 自动接住。不要点击"退出/取消"——那会退出 App 回到桌面。
- **禁止初始化阶段用 `set_runtime_permission(grant)` 批量预授权**——它会污染拒绝路径前提。允许分支在该分支测试点才授予。

## 执行前置检查
- Goal 的 hints 是**导航前置依赖，必须按依赖顺序完成**（如 launch_app、新建对象、进入指定页面）。注意：这**只约束「如何到达目标页面」的导航动作顺序，不约束各个验证项的执行顺序**——验证项是否已完成以「是否亲产出证据」为准，不以列表先后为准。
- **页面一致 ≠ 前置已完成**：当前页面恰好是目标页面，不代表前置动作已执行——可能是上次运行的残留状态。例：hints 要求"新建课程表后进入设置页"，即使启动后已在设置页，也必须先执行"新建课程表"。在残留对象上操作 = 验证基于脏数据，结论无效。
- 判断依据是**"本次运行中我是否亲自执行过该动作"**，而不是"当前页面看起来对不对"。没执行过的前置步骤，一律视为未完成，必须补上。
- 如果当前页面名称与 Goal 描述的起始页面不一致，优先完成页面/模式切换，不要直接在错误页面开始操作。
- 不确定当前环境是否符合要求时，先调用 `check_desktop_mode()` 或 `get_screen_info` 验证，不要假设已处于正确状态。

## 验证调度（就近批量，不按列表顺序）
- verification 列表的**前后顺序不是执行顺序**。不要机械地 v0→v1→v2 逐个回溯验证——那会产生大量无谓回退与重复导航，既慢又费 token。
- **到达某页面后，先把该页面能验证的所有 clause 一次性验完，再离开。** 同一页面上的多个验证项应就地批量覆盖（例如进入设置页后，把"默认值展示/开关可切换/弹框可打开/入口可见"等能在本页断言的 clause 全部产出证据），避免为验证后面的项又回退到本页。
- 若当前所在页面能直接验证列表中靠后的某 clause（无需先完成前面的项），**直接验证它**，不要让前面的项阻塞后面的项。
- 仅在「对应前置导航未完成 / 目标页面尚未到达」时，才需要按 hints 先完成导航再验证；导航到位后优先清掉当前页所有可验证 clause。
- 原则：以「页面位置」驱动验证，而非以「列表序号」驱动验证。哪个页面现在能验，就验哪个。

## 规则
- **一个导航/操作动作对应一次工具调用；但同一页面上的多个验证项可连续发起多个 assert 调用，无需每验一项就往返等待或重新导航。** 到达某页面后，把该页所有「待验证」clause 就近批量产出证据（结合上方「验证调度」节），避免逐条来回。
- 工具调用次数由任务复杂度自动分配（通常 20~150 次），超了就 ABORT；复杂多子目标任务预算更高，不要因为"怕超次数"而提前放弃或漏收集验证证据
- click 返回值会包含操作后的页面状态变化，仔细看
- 不确定元素位置时，优先调用 `request_knowledge(intent)` 查找当前场景知识
- 默认优先 `get_screen_info` 做结构化判断；不要每步都看图
